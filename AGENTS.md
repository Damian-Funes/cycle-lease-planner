# Project rules
- Capacity calculations are pure shared functions; diagnoses persist a full calculation snapshot so later configuration edits do not rewrite recorded technical assessments.
- Budget deep links apply a Typical and client/deal links independently, including when starting a new budget, to preserve diagnostic handoffs.
- Travel authorization uses database triggers as the authority; shared route validation helpers only provide early UI feedback.
- Route accounting reuses the activity completion dialog through optional callbacks and required-result props; existing callers retain their behavior.
- Legacy Júlia history stays read-only; never modify externally deployed julia-* functions. Travel voice uses distinct julia-viagem-* functions and transactional service-only RPCs to preserve route triggers and seller identity.
- Share Júlia labels, transcript parsing and call queries across budget, deal and reporting views to keep their interpretation consistent.- Multi-day trips keep `rotas.data_rota` equal to `data_inicio` via trigger so legacy readers keep working; "past trip" rules use `data_fim`, stop accounting opens at `data_inicio`.
- Seller departure base is data on `veiculos` (trip vehicle → seller vehicle → Maringá fallback), shared by frontend and toll function; never hardcode per-user bases.
- Trip routing (single path by stop order) and cost are pure functions in `src/lib/viagem.ts`; the toll edge function duplicates `assinaturaTrajeto` so an unchanged route never re-spends QualP credits.
- `rota_paradas.dia` is the realized day, written by the trigger in BRT when the stop is accounted (never planned); nights live in `rota_pernoites`, validated by trigger and required per night to conclude, so the DB stays the authority.
- Toll estimates are written only by the server function (trigger keeps client writes out); the seller-facing cost snapshot is frozen when sent for approval.
- Trip logbook/expense access windows live in SQL helpers (`fn_pode_escrever_diario`, `fn_pode_lancar_gasto`, `fn_pode_ver_rota`); `src/lib/viagemDiario.ts` mirrors them only for UI hints. Storage policies on the `viagens` bucket wrap UUID casts in `CASE bucket_id` + `fn_uuid_seguro` so other buckets never hit a cast error.
- Travel voice rules and extensible daily-pending contracts live under functions/_shared and are re-exported for frontend/tests; proposed SQL stays in docs/sql until explicit migration approval, and UI checks schema readiness before querying new tables.
- Visit debrief validation is shared by voice and tests and enforced again by SQL; the service-only voice transaction creates any confirmed next-step activity and stores its ID in the debrief atomically, without changing planning fields.
- Julia configuration queries fail independently and keep the card visible; the test trip selector queries only approved current-period routes without diary/expense joins to avoid unrelated access failures.
- Travel ElevenLabs configuration and provider-error sanitization live in a pure function-local helper so URL normalization, telephony selection, and credential redaction can be tested without making calls.
- Travel tool input normalization and schemas stay function-local and are tested without calls; validation logs include keys and sanitized issues only, never submitted values.
- Visit data feeds organizations through the immutable `organizacao_levantamentos` history, written only by a non-blocking `rota_paradas` trigger (later relato corrections append 'manual' rows); "current situation" is always derived by the `organizacao_situacao_atual` view, so no prior data is ever overwritten.
- Organizations have one-level `matriz_id` (validated by trigger; only admin/manager set it); attaching a company to a stop that had none is not replanning, so active trips stay approved.
- Trip pending rules have one source (`montarPendencias`, `completo` adds debrief gaps); Júlia's list and in-app notifications both use it, and notifications are synced (insert missing, mark vanished as resolved, never delete) by the server only.
- Activity resolution (done/reschedule/cancel) goes through SQL functions requiring a result/reason and logging reschedules; overdue reminders are synced into `notificacoes` by a service-only SQL function, so app, banner and future Júlia tools share one authority. The new-budget gate (revisions exempt) is enforced by an `orcamentos` insert trigger behind the `app_flags` switch; the UI hook only mirrors it.
- Organization completeness has one source: the `organizacao_completude` view / `fn_organizacao_faltas` (contact person with phone, city+UF, owner); UI hooks fall back to the same rule only before the migration. Discarding uses dedicated columns (never `status`) via `fn_organizacao_descartar`, and Júlia asks about at most one prioritized incomplete organization per call.
- Voice contact matching (exact > unique first name > unique approximate first name, ambiguous = no insert; in Júlia writes an unmatched name becomes a person only with `contato_novo_confirmado`, signalled to the levantamento trigger via a transaction-local setting, and `julia_completar_contato` links it afterwards) has one rule: SQL `fn_casar_pessoa_org` writes, `_shared/contatosOrg.ts` mirrors it for warnings/context; `rota_paradas.atividade_id` is the visit's own activity, the next step lives in `relato.atividade_id`.
- Júlia call dynamic variables come from one pure builder in functions/_shared/variaveisLigacao.ts, used by outbound (julia-viagem-ligar) and inbound (julia-viagem-entrada) so both stay identical.
- Júlia's `ja_sabemos` (busca, vínculo, contatos_paradas) is built only by `_shared/jaSabemos.ts` from the `organizacao_situacao_atual` view plus `pessoas.e_decisor`; loading failures omit it and never break the call.
- Julia spend: refused inbound calls live in `julia_ligacoes_recusadas` (never in `ligacoes_viagem`, to keep seller metrics clean); alert thresholds and prices live in `julia_gasto_config`, and the over-limit alert is raised by SQL `julia_finalizar_recusa`.
- Voice admin: only `ligacoes_viagem.papel_ligacao='admin'` plus the admin role may assign work to another seller; SQL `fn_julia_responsavel` forces the caller otherwise, and `_shared/vendedores.ts` only resolves spoken names to ids.
- Push (PushAlert) loads only on crmls.com.br via index.html; which notifications push is decided by `push_regras` key prefixes mirrored in `_shared/push.ts`, and only a real INSERT marks `push_status=pendente`, so upserts never resend.
- Public views use `security_invoker=true`; legacy dossiê/perfil-IA functions, trigger functions and unused views are executable only by service_role, so the anon key never reads data without RLS.
- Past-day trip pendings (nights without pernoite, days without visits) come only from `montarPendencias` and activate only when `rota_dias_sem_visita` loads, so voice never asks for what the DB cannot yet store; admin day-closing notices (`fechou:`/`caiu:`/`naofechou:`) are built by pure `_shared/fechamentoDia.ts`.
- Júlia's off-route stops are created only by service-only SQL `julia_adicionar_parada` (origem='julia', transaction-local `app.julia_parada_extra` skips reapproval and keeps the reported day); voice then reuses registrar_visita unchanged.
- Manual redial replaces only calls due ≤15 min; retorno/fechamento rows are reactivated, and a retorno is confirmed only if really `agendada` at that time.
- Hotel paid by the company is a `rota_gastos` row with `pago_pela_empresa=true` and null value; trip conclusion requires finance to fill the value, so the night closes by voice without inventing costs.
- Voicemail/no-answer on retorno/fechamento schedules one `retentativa_retorno` (+30 min, ≤22h) from the webhook via the pure `precisaNovaTentativa`; it is the only origin allowed as 4th automatic call. The "visited anyone else?" answer is a daily `rota_diario` entry read into `extras_confirmados` so `confirmar_extras` is asked once and never makes the cron dial.
- Commission: SQL `fn_comissao_orcamentos` returns amount, never cost; pure rules in `src/lib/comissao.ts`, latest version per number+org.
